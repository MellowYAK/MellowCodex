## 2. Permission model and effective precedence

Three UI labels for **local physical-control policy**:
- **Safe (proposed initial global default):** read/inspect/observe and clearly bounded non-mutating interactions only where allowed by the current task; no physical mouse/keyboard mutation, installation, launch/close or system change without an explicit separate owner authorization. Some reads can expose private data or trigger effects (e.g., web loads, screenshots, clipboard, network), so operation-specific sensitivity can still require confirmation or block.
- **Ask every action:** every effectful physical/UI/app/file/network operation gets a fresh owner authorization bound to a particular immutable operation; no blanket "Approve all" implied. Read operations follow specific risk metadata and current task scope. Failed/uncertain action is not automatically replayed.
- **Full control:** after a strongly authenticated **owner-only** local grant, permit task-authorized app-level physical automation within a visible target/scope and finite duration. Do not bypass task `allowed_tools`, model/host safety, Windows UAC/secure desktop, code review, Guard approval, secrets boundaries or policy-protected actions. An installation still requires the relevant task authorization and independent deployment review. UI must show who, which chats, target apps/paths, start/end, revocation and remaining duration; permanent unattended Full control is not default.

Data model (new owner-policy store, **not** Hub task DB used as authoritative owner source):
`owner_policy_revision`, `global_default_tier`, `chat_overrides[{chat_id, tier, revision, expiry|null, actor_owner_id, created_at}]`, `owner_grants[{grant_id, scope, target, action_digest, args_digest, task_id, task_revision, owner_policy_revision, chat_id, expires_at, consumed_at, actor_owner_id}]`, immutable append-only audit entries. `chat_overrides` absent/null means **INHERIT**, not silently Safe. Effective tier = active exact-chat override else global default, then intersect current task scope / capability risk ceiling / platform/OS restrictions. The owner **may** select multiple chat IDs for bulk overrides; apply with atomic owner-verified transaction and per-chat CAS preconditions; display exceptions/failures per chat. Never infer ownership from a project, current tab, ChatGPT user or chat correspondence. Newly created chats inherit default. A global change changes inherited chats immediately, not explicit overrides. Chats display both **Effective: Safe/Ask/Full** and **Source: Global / This chat**, with expiry.

Downgrades take effect immediately at **last safe dispatch boundary**: increment policy revision, invalidate unconsumed grants and reauthorize queued/proposed actions against current policy. For an action already dispatched or with uncertain effect, do not claim cancellation/rollback; mark **in flight / unknown** and require observe/reconcile before any retry. Do not silently terminate a running development task or release its pending action; defer unsafe continuation and provide precise status.

## 3. Owner identity and enforceable local boundary

**Required design gate before any implementation:** a dedicated native owner-broker under a distinct OS security principal/token or protected service identity whose private key/ACL cannot be read or modified by the Hub executor's actual Windows user SID, agent shell token, browser automation session, local web process or Guard. Only that broker persists owner policy and issues short-lived, one-time signed operation grants after an OS-mediated authentication **not available to the agent token** (e.g., Windows Hello with verified user presence/verification and protected key, a separately controlled credential/hardware security key, or credentialed secure desktop to a distinct owner principal). Document actual Windows user/process/token/SID isolation and key protection, deny impersonation/hijacked parent process. Same-user DPAPI or a click in the agent-controlled desktop **does not meet** this boundary. Without verified isolation: fail closed to Safe/Ask-unapproved; no Full control activation.

A locally rendered visible mode selector in the app header triggers a request to this broker; it never writes effective policy directly. The broker must refuse policy writes over MCP, PLAY, agent command, Guard MCP, generic localhost, agent REST, extensions or shell; do not publish a write RPC callable with the agent's credentials. Even a same-user program scripting the UI is not proof until separately authenticated via OS-protected challenge. Broker returns nonsecret policy status to Hub but never credentials/signing keys. Guard install credential remains independent and is not repurposed as owner approval.

**Residual limitations:** Any malware or human process possessing the owner token, elevated kernel privileges, or hardware/authenticator access can still bypass this design. Windows desktop session automation may overlap owner-visible UI: verify secure owner presence and transaction details in a trusted boundary; absence of such a boundary means effective security is advisory only. In all modes, user cannot bypass Windows UAC, secure desktop, ChatGPT host restrictions or higher-priority safety rules.

## 4. Operation-level risk metadata and enforcement points

One extensible **risk descriptor per operation**, not one label per skill:
`{operation_id, version_hash, effect_class, default_risk, target_types, resource_bounds, network_or_exfiltration, credential_use, reversibility, replay_safety, owner_confirmation_required}`. Suggested classes: R0 passive local metadata; R1 private reads/screen/clipboard/DOM extraction; R2 reversible app input, typing, navigation, file creation; R3 destructive filesystem/process/system changes, installs, credential/account use, outbound send/publish, external transfers; R4 protected/irreversible elevated operations (must have extra independent approvals or remain blocked regardless of Full). A single skill may expose multiple operation risk levels; a macro/PowerShell/JS command, browser script or Python extension with opaque arguments is **unknown-high-risk** until constrained by a reviewed per-operation adapter. **Unknown, new, unregistered, changed-version or changed-source-hash skill fails closed**, not Safe by name. A manifest's validated flag only proves prior tests and hash binding, never benign effect classification. Risk updates require code review/approved signed metadata and may not be supplied by the skill itself or prompt.

Apply one policy evaluator at the **final effectful tool dispatch**, plus the same checks at route-entry and queue release. Cover `ToolRunner.execute`, extension subprocess invocation, native desktop/app/window input, browser/PLAY, terminal/shell, file operations, model-driven code, documents, network transfers, app start/close, install and settings changes. All normal/SelfDevelop share evaluator; development guidance is an additional boundary, not a replacement. MCP/PLAY may inspect effective policy but cannot mutate/approve it. Guard bridge continues forwarding only under existing OAuth and independent Guard install/recovery controls; no owner-policy mutations through Guard. Some Guard recovery must work with Hub down, but without granting Hub or Guard the broker's owner credentials. No break-glass agent self-elevation.

For Ask grants bind **exact task_id + task_revision + action_id + canonical tool name + schema/version/hash + normalized argument digest + target identity + chat_id + policy revision + nonce + absolute expiry + one-time consume**. Protect against replay on retry, policy downgrade, task revision change, target/window/file identity change and TOCTOU by validation immediately before the effect. For unexpected redirects, child actions or changed arguments require new owner approval. A denied or expired grant yields a concrete `policy_denied / owner_approval_required` receipt, with `input_sent=false` and `effect_started=false`; if effect uncertain, emit `effect_unknown` and reconcile, never fabricate success.

Keep `allowed_tools` intersection, task cancellation/revision, browser observation freshness, existing action review and Guard independent code deployment authorization. **Full ≠ owner approval to change the rules or deploy unchecked code.**

## 5. UI/UX specification (local owner interface, not agent-controlled authority)

Persistent header selector: `Permission: Safe ▾` / `Ask every action ▾` / `Full control (14m left) ▾`. Always show **Global default** and **This chat: Inherit / Override**; tooltip explains task-specific limits. In the chat picker show checkbox bulk selection, mixed states, inherited values, confirmation preview of impacted chat IDs and one atomic transaction. Changes require broker authentication and clear before/after summary. No stealth switch.

For Full control: modal must display selected app/window/process identity, allowed domains/paths/actions, specific chat(s), local start/end (default proposed max 15 minutes; owner selects shorter; never indefinite without a separately decided policy), and `Stop Full control` with broker-backed revocation. A persistent header countdown and owner-only revoke control remain visible; on expiry, lockdown/recheck queues. For Ask every action, the local approval prompt displays exact task/chat/action, target, formatted arguments (with secrets redacted), consequences, validity (proposed 60 seconds), and independently authenticated Approve one / Reject. Never assume an agent clicking either button is consent. If owner broker cannot establish trusted user presence, do not offer functional Full mode.

## Decisions and recommended defaults for owner review

1. **Broker identity:** require distinct Windows owner user / protected service plus verifiable hardware/Hello-based presence. The exact feasible design is **not established from repo source**; implementation blocked pending owner-environment feasibility check. Avoid any pretend security from loopback/same-user secrets.
2. **Default global tier:** Safe. New chats inherit; existing chats initially inherit unless owner explicitly selects overrides. No automatic migration to Full.
3. **Full control grant:** per selected chat(s) + app/window/path/domain resource scope, visible countdown, 15-minute maximum candidate default, expires on broker/Hub restart (owner can shorten).
4. **Ask authorization:** one operation, maximum 60 seconds, no reusable wildcard, verified exact action args/revision and one-time consumption.
5. **Bulk edits:** exact selected chat IDs, atomic CAS, no silent overrides of running work; owner review. UI may show mixed inherited/override states.
6. **Policy application:** block unknown or changed skills/opaque shell and browser scripts pending per-operation review; do not mark all 100 researched skills installed or safe.
